Campus Voice — Comprehensive Technical Guide

Full-Stack Architecture, Technology Rationale, and Viva/Interview Reference
Target System: Institutional Announcement & Peer Q&A Portal Stack: Vanilla JS, HTML5, Tailwind CSS, PDF.js, Node.js Native HTTP Port: 3000

1. Executive Summary & Problem Solved

In engineering colleges, critical communications (exam circulars, lab timetables, on-campus drive schedules, hackathon calls) are typically distributed through unorganized WhatsApp groups, unofficial social channels, or physical bulletin boards. This causes circular loss, unverified rumors, and communication friction.

Campus Voice solves this with a unified, dual-module institutional web portal:

  • Official Notice Board: Faculty-published circulars with branch targeting (CSE, AIML, ECE, ME, CV), category filtering, upvoting, bookmarking, and high-fidelity PDF/image attachment previewing.
  • Student Community Q&A: A moderated peer-to-peer discussion forum (StackOverflow/Reddit style) categorized into topics (Placements, Exams, Projects, Academics, Hostel), featuring verified faculty responses, accepted answer resolution, anonymous posting, and community reporting.

4. Core Architectural Systems: Deep Dives

A. Role-Based Access Control (RBAC) via CSS Hierarchy

Rather than executing heavy DOM manipulation loops to query and hide role-specific buttons on every render, role visibility is handled directly by the browser's CSS rendering engine:

The Strict Role Display Architecture:
.faculty-only { display: none !important; }
body.role-faculty .faculty-only { display: block !important; }
.student-only { display: none !important; }
body.role-student .student-only { display: block !important; }

When a user logs in, JavaScript simply executes document.body.classList.add("role-faculty"). The browser instantly reflows and displays faculty controls (e.g., "Post Notice", "Delete", "Add Category") while keeping students restricted. This architecture makes role transitions instantaneous and impossible to break via accidental inline style changes.

B. XSS Defense & Input Sanitization

Because notices and Q&A threads are injected dynamically into the DOM using template literals, the application incorporates a rigorous Cross-Site Scripting (XSS) defense layer:

  • escapeHtml(str): Replaces &, <, >, and " with HTML entities to neutralize script injection.
  • escapeJs(str): Neutralizes quotes and special characters within inline event handler arguments (e.g., onclick="openFileViewer('${escapeJs(fileId)}')").

C. Flash-of-Unstyled-Content (FOUC) Dark Mode Architecture

To prevent the jarring "white flash" that occurs when dark mode is initialized after CSS loads, a synchronous, blocking script is placed directly in the <head> of index.html:

const saved = localStorage.getItem("campusTheme");
const prefersDark = window.matchMedia("(prefers-color-scheme: dark)").matches;
if (saved === "dark" || (!saved && prefersDark)) document.documentElement.classList.add("dark");

This executes before the browser paints its initial frame, ensuring seamless dark mode rendering from millisecond zero.

D. Chunked Streaming Binary File Uploads

Unlike frameworks requiring third-party libraries like Multer, server.js natively consumes binary streams:

  1. Incoming POST /api/files/:id requests stream raw data chunks into memory.
  2. Buffer.concat(chunks) stitches the payload together into a single atomic buffer.
  3. The buffer is written directly to data/uploads/{fileId} while headers (X-File-Name, X-File-Type) are persisted to a companion JSON metadata file ({fileId}.meta.json).
  4. When requested via GET /api/files/:id, the server sets correct Content-Type and Content-Disposition: inline headers, allowing PDF.js or browser image decoders to display the file natively.

5. Viva / Technical Interview Q&A Cheat Sheet

Q1: Why didn't you use React, Next.js, or Vue for this project?
Answer: "For an institutional campus intranet, Vanilla JavaScript provides zero build dependencies, instant startup, sub-50ms load times, and a near-zero memory footprint. It avoids build-tool vulnerabilities, npm supply-chain bloat, and framework deprecation cycles while giving complete mastery over the DOM."
Q2: Why did you build the server with Node's native HTTP module instead of Express?
Answer: "By avoiding Express, our backend has zero third-party dependencies and runs entirely on Node.js core. This guarantees negligible memory usage (~20 MB), lightning-fast execution, and complete elimination of npm package vulnerabilities. It also showcases fundamental knowledge of HTTP protocols, streams, and file I/O."
Q3: How does the in-app PDF preview work without forcing a file download?
Answer: "We integrated Mozilla's PDF.js library. When a user clicks 'View Attachment', the client fetches the binary PDF as an ArrayBuffer. PDF.js decodes the PDF's vector stream and renders each page directly onto an HTML5 <canvas> element, calculating device-pixel-ratio scaling for sharp rendering on retina screens."
Q4: How does the system handle multi-browser synchronization?
Answer: "The server enforces CORS headers (Access-Control-Allow-Origin: *). If a faculty member on Chrome posts a circular or accepts a student's answer, it is atomically committed to the backend JSON store. When a student on Edge or a mobile browser loads or refreshes their feed, the updated state is immediately fetched and reflected."
Q5: How would you scale this architecture to support 10,000+ simultaneous students?
Answer: "1. Replace flat JSON storage with an indexed database like PostgreSQL (with connection pooling) or MongoDB.
2. Offload uploaded file storage from local disk to AWS S3 or Cloudflare R2 behind a CloudFront CDN.
3. Implement JWT-based authentication with bcrypt-hashed passwords.
4. Integrate WebSockets (or Server-Sent Events) to push real-time circular notifications without manual refreshes."
